## Architecture overview
One Rust service (`apps/api`) owns all reads and writes and the only database, Postgres. Every other part is a client of its public HTTP API under `/v1`:

```
 web (Nuxt, SSR) ─┐
 app (Tauri) ─────┤
 consumer apps ───┼── HTTPS /v1 ──> api (Axum) ──> Postgres
   via SDKs       │
 scripts, agents ─┘
   (mcp in v2, via the Rust SDK)
```

- The OpenAPI spec is generated from the Rust code with `utoipa` and committed as `openapi/openapi.json`. It is the contract: the TypeScript client (`packages/api-client-ts`) and every SDK's transport layer are generated from it.
- `web` and `app` share screens, components, composables and the API client through `packages/ui`. They hold only routing, layouts and platform-specific code.
- Inside `api`, the reference-data read path and the metric ingestion write path are separate modules, so they can be tuned or split later without touching each other (principle 5).
- No second data store in the MVP. Reference reads are made fast with in-process caching and HTTP cache headers, not a separate server or Redis (principles 3 and 4).

## Repository and workspace
- Monorepo tooling: see ADR-001. A **Cargo workspace** holds `apps/api`, `apps/mcp`, `packages/types`, `sdks/rust` and `apps/app/src-tauri`. A **pnpm workspace** holds `apps/web`, `apps/app`, `packages/ui`, `packages/api-client-ts` and `sdks/ts`. `sdks/dart` is a standalone Dart package.
- Dependency rules: apps may depend on packages; packages never depend on apps; apps never import from another app's folder. SDKs depend only on the contract and, for Rust, `packages/types`.
- Generated code: `openapi/openapi.json`, the generated part of `packages/api-client-ts` and of each SDK, and the SQLx offline query data (`.sqlx/`, from `cargo sqlx prepare`) are committed and never edited by hand. CI regenerates them and fails if they differ.
- Code style: `rustfmt` and `clippy` (warnings as errors in CI) for Rust; ESLint and Prettier for TypeScript and Vue; `dart format` and `dart analyze` for Dart.

Commands are listed in the README [Commands](../README.md#commands) table, not here.

### API contracts
The contract is `openapi/openapi.json`, generated by `api`. There is one server, so there are no server-to-server contracts in the MVP.

| Provider | Contract | Consumers | Consumer auth | Compatibility rule |
|---|---|---|---|---|
| api | openapi/openapi.json | web, app, packages/api-client-ts | Admin session; PATs for scripts | Installed-client window (below) for app |
| api | openapi/openapi.json | sdk-ts, sdk-dart, sdk-rust and the apps that embed them | Project keys (publishable in client apps, secret on servers) | Installed-client window (below) |
| api | openapi/openapi.json | mcp (v2), through sdk-rust | PAT or agent-scoped project key | Same as SDKs |

### API compatibility
- Clients and SDKs use code generated from `openapi/openapi.json`; nobody hand-writes request shapes (principle 2).
- Versioning: additive changes only within `/v1`; a breaking change needs `/v2` (BR-008). CI compares the generated spec with the default branch and fails on a removed or changed field or endpoint unless the PR is labelled `impact:breaking` and has an ADR.
- Installed clients (the Tauri app, and every app that embeds an SDK) cannot be force-updated. The API supports every app and SDK version released in the last TBD months.
- Breaking a field or endpoint: add the replacement → release clients and SDKs that use it → wait out the compatibility window → remove the old one. Record each step in an ADR.
- Forced upgrade: the app checks API-014 at startup and shows an "update required" screen below the minimum version. SDKs send their version with every request (`sdk: ts/1.2.0`), so usage of old versions is visible before support ends.

## Error handling
- Every error response has the body `{ "error": { "code": "project_not_found", "message": "…", "request_id": "…" } }` (NFR-001). Codes are stable `snake_case` strings listed in the OpenAPI spec; messages may change.
- Status codes: 400 validation (with per-field details), 401 missing, invalid, expired or revoked credential, 403 missing scope, 404 not found, 409 conflict (for example, duplicate slug), 413 batch too large, 429 rate limited, 500 unexpected. A 500 never includes internal details.
- Dashboards show the message and, for unexpected errors, the request ID so a problem can be traced.
- SDKs never throw into app code; failures go to an optional debug logger (NFR-006). Sends retry with exponential backoff and jitter up to a limit; 4xx responses other than 408 and 429 are not retried.
- The Tauri app shows cached data with an "offline" banner when the API is unreachable; writes are not queued in the MVP.

## Logging and observability
- `api` logs structured JSON with the `tracing` crate. Every request gets a request ID (taken from an incoming `X-Request-Id` or generated), returned in the response header and the error body, and recorded in audit entries.
- Never logged: full keys or tokens (prefix only), passwords, session tokens, event `properties` (they may contain personal data).
- Platform Core reports its own metrics through its SDK (FR-034); errors in web and app are reported as `error` events.
- Metrics, tracing and alerting: TBD with D1. Alerts on its own health are in DEPLOYMENT.md (F19 adds alerts for other projects in v2).

## Security and privacy
- Client apps (web, app, and every consumer app) are public: their code and configuration ship to users. They hold no secrets and only ever get a publishable key (BR-002). All authorization is enforced in `api`.
- Credentials: keys and tokens are random, at least 32 bytes of entropy, prefixed (BR-006), stored as SHA-256 hashes and compared in constant time. The admin password uses Argon2id. Key and token creation and revocation need an admin session; no key or token can create another.
- Scopes are checked on every endpoint; project keys only reach their own project.
- Rate limits per key, per token and on login (FR-025).
- Transport: HTTPS only in staging and production; HSTS on web.
- Personal data: the MVP stores the admin's email. Event properties come from consumer apps and may contain personal data; the SDK documentation tells app developers not to send it, retention is limited (D3), and properties are never logged.
- The dashboard session design (cookie or token, CSRF protection, Tauri storage) is ADR-008.
